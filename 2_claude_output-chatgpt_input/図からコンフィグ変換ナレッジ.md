# 物理・論理合成図（drawio）→ NW機器コンフィグ 変換ナレッジ

> **この文書の使い方**
> 新しい物理・論理合成図（drawio 形式）を受け取ったAIが、**この文書と図だけ**を読んでNW機器のコンフィグを書き起こし、図の矛盾を人がレビューできる形で出力するための手順書です。書籍などの元資料は不要です。
> 必要な前提知識（図の表現規約、コンフィグへの対応規則、推論の優先順位、チェック観点、出力書式）はすべてこの文書に含めています。

- 版: 1.1（2026-11-23）。変更履歴は末尾
- 付属ツール: `tools/drawio_nwdiag_extract.py`（標準ライブラリのみ・Python 3.8+）
- 作例: `example_BPDF/`（BPデータファームの東京・大阪構成の指摘一覧）。**書式の参考用で、AIに変換させる入力には含めない**（1.1）

## 1. 入力・出力・作業の全体像

### 1.1 入力

| 入力 | 必須 | 説明 |
|---|---|---|
| drawio ファイル（`.drawio` / `.drawio.svg` / `.xml`） | 必須 | 「物理・論理合成図」ページを含むもの。同じファイルに論理構成図・物理構成図ページがあれば補助に使う |
| 対象ページ名 | 任意 | 指定がなければページ名に「合成」「物理・論理」を含むページを選ぶ。カラー版とモノクロ版がある場合はカラー版（色でセグメントを区別できるため）を主とし、もう一方との差分も確認する |
| 機種・OSの指定、IP管理表、命名規約 | 任意 | 与えられたら図より優先して使う（6章） |
| プロジェクト既定値 | 任意 | 図からは決まらないが、プロジェクトで書き方を揃えたい値（下表）。未指定の項目は本書の既定値を使い、変換レポートの「既定値を使った項目」（8.1）に一覧で出す |

**プロジェクト既定値の項目**（指定が無ければ右列の本書既定値）

| 項目 | 指定の例 | 本書の既定値 |
|---|---|---|
| LAG モード | `on`（static）/ `active`（LACP） | LACP active（R5, 6.2） |
| 冗長化プロトコルと書式 | VRRP 旧書式（`vrrp N ip`）/ VRRPv3（`fhrp version vrrp v3`）/ HSRP | 凡例のプロトコル。書式は VRRPv3（10.1） |
| 冗長化の優先度・グループ番号の規則 | 01号機 105、グループ番号＝VLAN ID | 01号機 110・プリエンプト有効、グループ番号＝VLAN ID（6.2） |
| 管理 VRF の名前 | `mgmt` / `Mgmt-vrf` | 図の vrf 箱の名前、無ければ `mgmt` |
| trunk に付けるコマンド | `switchport nonegotiate`、`switchport trunk encapsulation dot1q` | 付けない |
| 冗長ペアの02号機の出力形式 | 全文 / 差分表 | 全文（8.1） |
| ルーターで同一セグメント2ポートの実装 | L2 スイッチポート＋SVI / BDI（EVC） | L2 スイッチポート＋SVI（4.2） |
| 未使用ポートの扱い | shutdown する / 設定しない | 設定しない（6.2） |

利用者に期待する書式（既存のコンフィグ、社内標準、参考書籍の書式など）があるなら、ここで指定する。既定値の違いは誤りではないので、比較・レビューのときは「既定値を使った項目」の表を見て差を切り分ける。

### 1.2 出力（3点セット）と対象範囲

**コンフィグを作る対象**

| 図の要素 | 扱い |
|---|---|
| 箱に Vendor Model があるネットワーク機器（FW、ルーター、L3/L2 スイッチ、管理SW） | **コンフィグを生成する** |
| 無線AP（型番不明・コントローラー管理が前提のもの） | コンフィグは作らず、**設定項目表**（管理IP、接続ポート、VLAN/SSID の対応、給電）だけを出す。型番が指定されていて単体設定する機種なら生成する |
| サーバー、VM、仮想スイッチ、回線終端装置、ISP 側機器 | **対象外**。ただしスイッチ側の設定根拠に使い（2.8）、その中の描画ミス（線の未接続、色の不一致など）は7章のチェック対象にする |

対象範囲を揃えるのは、変換結果どうしの比較やレビューをしやすくするため。範囲を変えたい場合は依頼文（9章）で指定する。

**出力**

| 出力 | ファイル名例 | 内容 |
|---|---|---|
| A. 変換レポート | `<図名>_config.md` | 機種判定、抽出サマリ、機器ごとのコンフィグ、設定行ごとの根拠表 |
| B. 指摘一覧（レビューシート） | `<図名>_review.md` と `<図名>_review.csv` | 図の矛盾・誤記・不足・設計上の注意。人が確認状態を記入して使う |
| C. 未確定値リスト | Aの末尾、または `<図名>_tbd.md` | `<TBD>` にした値の一覧と、決めるべき人・情報源 |

### 1.3 作業ステップ

| Step | 作業 | 参照章 |
|---|---|---|
| 0 | 図のページ一覧を確認し、対象ページと補助ページ（論理構成図など）を決める | 3.1 |
| 1 | 図の**凡例を最初に読む**（色・線種・記号・バッジの意味）。凡例が本書の既定規約と違うときは**凡例を優先**する | 2.9 |
| 2 | 抽出ツールで構造化データ（機器・ポート・セグメント・リンク・ペア）を作る | 3.2 |
| 3 | 画像化した図と目視で突き合わせ、ツールの分類ミスを補正する | 3.4 |
| 4 | 機種・OSを特定し、記法を決める（特定できなければ Cisco フォールバックとし、理由を書く） | 4 |
| 5 | 拠点・セグメント台帳、結線表、ポート所属表を作る（中間表現） | 5.1 |
| 6 | 機器ごとにコンフィグを生成し、根拠ラベルを付ける | 5, 6 |
| 7 | 整合性チェックを全項目実施し、指摘一覧に記録する | 7 |
| 8 | 3点セットを出力する | 8 |

**原則**
- **コンフィグは図の設計意図を写すもの、指摘一覧は懸念を書くもの、と役割を分ける。** 図に描かれた接続・VLAN 所属・アドレス・経路は、設計上の懸念（L2 ループ、冗長性不足、セキュリティ上の心配など）があっても、**コンフィグから削除・コメントアウト・shutdown しない**。懸念は指摘一覧に WARN で記録し、コンフィグには該当行に `! WARN R-xxx` のコメントを付けるだけにする。
- 図と違う設定にしてよいのは、**図の値のままでは設定が成立しない場合だけ**（アドレス重複、同一ポート名の重複、明らかな誤記など。6.4）。そのときも指摘一覧に ERROR/WARN で載せ、どちらを採ったかを書く。
- 図に書いてあることは、勝手に「正しい値」に直さない。矛盾していればコンフィグでは暫定値を選んでもよいが、**必ず指摘一覧に載せる**。
- 図に無い設定（経路、VLAN、ポートなど）を「あった方がよい」という理由で足さない。提案は指摘一覧に書く（5.5）。
- 図に無い値を作るときは、**必ず【推測】ラベルを付ける**。IPアドレスのように実運用に直結する値は、推測できても `<TBD>` を基本にする（6.3）。
- 同じパターンが省略されている図が普通にある（2.10）。省略と誤りを区別する。

## 2. 物理・論理合成図の表現規約（図の読み方）

### 2.1 物理・論理合成図とは

物理構成図（機器・ケーブル・ポート）を土台に、各機器を**大きな箱**として描き直し、その中に論理構成（ポート、L2セグメント＝VLAN、ルーティングテーブル、仮想マシン）を書き込んだ図です。「どの物理機器・物理ポートで、どの論理ネットワークを実現するか」の対応を示し、設計の矛盾を机上で検証するために使います。L1（物理）と L3（IP）を、L2（VLAN）でひも付けて1枚にしたものと考えてください。

主な読み取り対象は次の4種類です。
1. **ポート**（物理ポート、論理ポート＝LAG・VLAN IF・仮想NIC）
2. **ネットワークセグメント**（VLAN。1つの機器・ケーブルに複数重ねられる）
3. **ルーティング**（GRT＝グローバルルーティングテーブル、VRF）
4. **仮想マシンと仮想スイッチ**（サーバーの箱の中）

### 2.2 図形要素の意味（既定規約）

| 図の要素 | 意味 | 典型的な見た目 |
|---|---|---|
| 機器の大きな箱 | 物理機器1台 | 角丸または四角の枠。左上（または右上）に小さなアイコン枠 |
| 箱の近くのテキスト「Host / Vendor Model」 | ホスト名（1行目）と機種（2行目） | 例: `xx1-core01` / `A社 L3SW 5000-48` |
| 箱の縁に並ぶ小さな箱 | 物理ポート。ラベルはポート名 | `Te0/1`, `Gi0/24`, `Mgmt`, `eth1`, `BMC` |
| 複数ポートにまたがる箱 | リンクアグリゲーション（LAG / Port-channel） | `Po1` |
| 箱の中央付近の灰色の箱 | ルーティングテーブル | `GRT`（グローバル）、`vrf <名前>`（VRF） |
| 箱内の色付き横線（太線・中抜き） | L2セグメント（VLAN） | 色ごとに1セグメント |
| 横線から点線で引き出されたラベル | セグメント名・VLAN ID・ネットワークアドレス | `10.1.10.0/24 DMZ, VLAN10` |
| 横線上の小さな色付きバッジ | そのセグメントでのルーティング機能（またはノード）のIP。**第4オクテットのみ**を書く | `.1`, `.4`, `.x`, `.x+1` |
| ルーティング箱どうしを結ぶ太い半透明線＋`vip .N` | 冗長化ペア（VRRP/HSRP）と仮想IP | 色はセグメント色、または灰色（複数セグメント共通） |
| ポート・Po・ルーティング箱とセグメント横線を結ぶ細線 | 「そのポート/IFがそのVLANに所属する」 | 線の色はセグメント色 |
| 機器間の線 | 物理ケーブル | 太さ・端点記号でケーブル/コネクタ種別を表す（2.4） |
| 「×2」と楕円 | 同じ区間に複数本のケーブル | 物理構成図で多い |
| 大きな枠（ラック、フロア） | 物理的な配置単位（ラック、フロア、拠点） | 機器ではない |
| 機器の外側の注記テキスト | 設計ルールの補足 | 例「業務アプリごとにVLAN100-199の範囲から割り当てる」 |

### 2.3 セグメント（横線）の読み方

- **横線1本＝1つのL2ドメイン（VLAN）**。ただしラベルが `VLAN100-199` のように範囲なら、「同じポリシーの VLAN 群をまとめて1本に描いた」もの（集約表現）。個々の VLAN は図に無いので、テンプレート化する（5.4）。
- ラベルは `<ネットワークアドレス>/<長さ> <セグメント名>, VLAN<ID>` の形が基本。ネットワークアドレスが範囲の集約（例 `/18`）なら、その中から個々のサブネットを切り出す前提。
- **ルーティング箱より上の横線**は外部接続側（上流）、下は内部（下流）。位置にも意味がある。
- 色の意味は凡例か、ラベルとの対応から決める。同じ色は図全体で同じセグメント種別を表すのが原則。

### 2.4 ケーブル・コネクタ（線の太さと端点記号）

凡例がある場合は凡例に従う。よく使われる規約の例は次のとおり（凡例が無い図の既定値として使ってよいが、【推測】扱い）。

| 線 | 端点 | 意味 |
|---|---|---|
| 細線 | 記号なし | RJ45 / 1000BASE-T |
| 細線 | 白丸 ○ | SFP+/RJ45（10GBASE-T モジュール）で 1000BASE-T を収容 |
| 細線 | 黒丸 ● | SFP/LC / 1000BASE-SX |
| 太線 | 黒丸 ● | SFP+/LC / 10GBASE-SR |

端点記号は**その端のポート側**のモジュールを表す（両端で違うことがある）。

### 2.5 IPバッジの読み方

- 数字 `.4` は「セグメントのネットワークアドレス＋第4オクテット」。例: `10.1.0.0/27` 上の `.4` は `10.1.0.4/27`。
- `.x`, `.y`, `.x+1` は**値が未確定**という意味（規則だけ決まっている）。
- 冗長ペアの両機器のバッジ（例 `.1` と `.2`）と `vip .3` を組で読む。ルールが別記されることもある（例「`.1/.2/.3 (01/02/vip)`」＝01号機/.1、02号機/.2、VIP/.3）。
- ドットが無い数字（`2`）は誤記の可能性がある。指摘一覧に載せる。

### 2.6 ルーティング箱（GRT / VRF）

- `GRT` はグローバルルーティングテーブル。L3機器（ルーター、L3スイッチ、FW）が持つ。
- ルーティング箱とセグメント横線の接続＝「そのセグメントにL3インターフェースを持つ」。L3スイッチでは **SVI（`interface VlanN`）**、ルーターでは物理IF（サブIF）または BVI/SVI。**図では SVI の箱を省略することが多い**（ベンダーの規則で名前が自動的に決まるため）。省略されていても、接続線とバッジがあれば SVI を作る。
- `vrf <名前>` 箱は独立したルーティングテーブル。そこに接続するポートは VRF に入れる（例: `vrf mgmt` ＋ `Mgmt` ポート＝管理用VRFを使った OOB 管理）。
- 1台に複数の VRF 箱がある場合は、論理的に別ルーターとして扱う（VRF 間の通信は経路漏洩などが図に無い限り行わない）。

### 2.7 冗長化ペア

- ルーティング箱どうしの太い半透明線が冗長化ペア。`vip .N` が仮想IP。凡例で VRRP か HSRP かが分かる。分からなければ、記法として採用したベンダーの標準（Cisco なら HSRP も選べるが、標準プロトコルの VRRP を既定とする）を選び、【推測】とする。
- 灰色の線に `vip .3` が1つだけ描かれている場合、「複数の内部セグメントで同じ規則（vip=.3）」という意味の集約表現。全 SVI に展開する。
- グループ番号、優先度、プリエンプト、タイマーは図に描かれないのが普通（6章）。

### 2.8 サーバー・仮想化の表現

- 物理サーバーの箱の中に、仮想スイッチ（`vSwitch0` など）と VM の箱がある。VM の `eth0` を仮想スイッチ内のセグメント横線に結ぶ。
- 仮想スイッチのアップリンクがサーバーの物理NIC（`eth1`, `eth2`）につながり、NIC から物理スイッチへのケーブルが描かれる。
- **スイッチ側ポートの VLAN は、サーバー内の仮想スイッチのセグメントから決まる**（DMZ と COMMON の VM があるサーバーなら、接続ポートは VLAN10,11 の trunk）。
- `BMC` はサーバー管理モジュールの管理ポート（管理VLANの access）。
- サーバーや VM 自体はNW機器ではないのでコンフィグ対象外。ただしスイッチ側の設定根拠に使う。

### 2.9 凡例の扱い

1. 図中に凡例（Legend）枠があれば、**最初に読む**。本章の既定規約より凡例を優先する。
2. 凡例の線・図形はどこにも接続されていないことが多い。抽出ツールではこれを「free（端点なし）」として分類する。ここから線幅・端点記号と意味の対応表を作る。
3. 凡例に無い表現が本体にあれば、指摘一覧に「凡例未定義」として載せる。

### 2.10 よくある省略（誤りではないもの）

| 省略 | 扱い |
|---|---|
| 冗長ペアの片方（例 02号機）の箱の中のセグメント線が描かれず、ルーティング箱とバッジだけある | 対になる機器と同じ構成と推定（【推測】対称性）。指摘一覧には INFO として記録 |
| 同じ構成のサーバーやラックの一部だけ描く | 描かれたものだけを設定し、パターンから推定できるポートはコメントで示す |
| 同じ構成のフロアを1つだけ描く | 同上。他フロアは「同パターン省略」と注記 |
| SVI（Vlan IF）の箱 | 2.6 のとおり、ルーティング箱と横線の接続から SVI を作る |
| 接続しないポート | 描かれない。未使用ポートの扱い（shutdown 等）は設計ルールとして別途確認 |

## 3. 図データの抽出手順

### 3.1 drawio ファイルの構造（AIが手で読む場合の知識）

- `.drawio.svg` は SVG の `<svg ... content="...">` 属性に、HTML エスケープした `<mxfile>` XML を持つ。`.drawio` は `<mxfile>` そのもの。
- `<mxfile>` の下にページごとの `<diagram name="ページ名">`。中身が `<mxGraphModel>` でなく文字列なら、**Base64 → raw deflate 展開 → URLデコード**で XML に戻す。
- 図形は `<mxCell vertex="1">`、線は `<mxCell edge="1" source="id" target="id">`。`<object>`/`<UserObject>` で包まれていれば、ラベルは `label` 属性、**カスタムプロパティ**（VLAN ID などを持たせている場合がある）はその他の属性。
- 座標は親（`parent`）からの相対値なので、親をたどって絶対座標にする。線のラベルは線を親に持つ子セルの値。
- `style` 属性: `fillColor`/`strokeColor`（色）、`strokeWidth`（太さ）、`startArrow`/`endArrow`=`oval` と `startFill`/`endFill`（端点の丸と、その塗り）、`dashed=1`（点線）。
- **線の source/target が空**の場合、その端は図形につながっていない（見た目では接していても）。これが「線の未接続」の検出根拠になる。

### 3.2 抽出ツールの使い方

```bash
# ページ一覧
python3 tools/drawio_nwdiag_extract.py diagrams.drawio.svg
# 対象ページを抽出（Markdown と JSON）
python3 tools/drawio_nwdiag_extract.py diagrams.drawio.svg --page "物理・論理合成図_4C" --md out.md --json out.json
```

出力される内容:

| 節 | 内容 | 使い道 |
|---|---|---|
| 1. 機器 | ホスト名・機種・枠。同名機器は `#2` を付けて区別 | 機器一覧、ホスト名重複の検出 |
| 2. 機器ごとの要素 | port / portchannel / segment（横線）/ ipbadge / routing / vip / seglabel | 機器内の論理構成 |
| 3. 物理リンク | 機器間のポート同士の線（端点 ●○-、線幅、色、線ID） | 結線表 |
| 4. 論理接続 | ポート・Po・ルーティング箱とセグメント横線の接続 | VLAN 所属、SVI |
| 5. 横線→ラベル | 横線とセグメントラベルの対応 | セグメント台帳 |
| 6. ルーティング箱どうしの線 | 冗長ペア候補 | VRRP/HSRP |
| 7. 機械チェックの警告 | ホスト名重複、線の未接続（機器・サーバー・VM の中の線を含む）、ポートの多重接続、速度表記の矛盾、CIDR重複、所属線の色の不一致、ラベルへの接続 | 指摘一覧の初期値 |
| 8. 分類できなかった線 | 端点の無い線（凡例、VRRP線など）、その他 | 目視確認 |

**ツールの限界（必ず目視で補う）**
- 機器の帰属は「要素の中心が入る最小の機器枠」で判定している。枠が重なる図では誤判定がありうる。
- 横線の色だけでセグメントを識別しているので、同じ色が別の意味で使われている図では誤る。
- 端点を接続せずに描かれた線（ラベルやペア線など）は「分類できなかった線」に入る。座標から意味を判断する。
- 警告の種類とチェックIDの対応: HOSTNAME_DUP＝N-01、EDGE_DANGLING＝P-01、PORT_MULTI_LINK＝P-02、SPEED_MISMATCH＝P-03、CIDR_CONFLICT＝A-01、LINE_COLOR_MISMATCH＝D-03、EDGE_TO_LABEL＝D-04。
- 画像としてのレンダリングは行わない。目視確認には drawio で開くか、SVG/PNG を画像として見る。

### 3.3 中間表現を作る

抽出結果から、次の4表を作る（変換レポートにも載せる）。

1. **機器台帳**: ホスト名（重複は仮称を付与）、機種、役割（FW/RT/L3SW/L2SW/管理SW/AP/サーバー）、拠点、冗長ペアの相手
2. **セグメント台帳**: 拠点、色、セグメント名、VLAN ID（範囲）、ネットワークアドレス、ルーティング箱のIP（機器ごと）、VIP
3. **結線表**: A機器・Aポート・端点、B機器・Bポート・端点、線種（凡例による意味）、LAG
4. **ポート所属表**: 機器・ポート（Po）ごとの所属セグメント（1つなら access、複数なら trunk）

### 3.4 目視での突き合わせ

- 図を画像で確認し、中間表現の各行が図の見た目と一致するかを確かめる（特に線が交差する場所、ジャンプ記号のある場所）。
- 「ラベルは描いてあるが線が来ていない」「線が横線に届いていない」ものは、未接続として扱う。

## 4. 機種の特定と記法の決定（Cisco フォールバック）

### 4.1 特定の手順

1. **利用者からの指定**（機種・OS・バージョン）があれば最優先。
2. 図の Vendor Model 欄の記載を読む。実在のベンダー名・型番（例 Cisco Catalyst 9300、Juniper EX4300、FortiGate 100F）が読めれば、そのOSの記法を使う。
3. ポート名の命名規則から推定する（参考情報。単独では確定しない）。

| ポート名の例 | 示唆されるOS |
|---|---|
| `Te0/1`, `Gi1/0/1`, `Po1`, `Vlan10` | Cisco IOS / IOS-XE |
| `Ethernet1/1`, `port-channel1`, `mgmt0` | Cisco NX-OS（または Arista EOS） |
| `xe-0/0/0`, `ge-0/0/0`, `ae0`, `irb.10` | Juniper Junos |
| `port1`, `wan1`, `internal` | Fortinet FortiOS |
| `ethernet1/1`, `ae1` | Palo Alto PAN-OS |
| `1/1/1`, `lag 1` | Aruba AOS-CX |

4. 機種名が架空（「A社 L3SW 5000-48」など）・空欄・一般名だけ（「L3SW」）の場合は、**特定不能**としてフォールバックする。

### 4.2 Cisco フォールバックの既定

| 図の役割 | フォールバック先（記法の基準） | 主な理由 |
|---|---|---|
| L3スイッチ（GRT＋多数のVLAN） | Cisco Catalyst 9000 系 / IOS-XE | 企業ネットワークで最も普及した L3SW の記法で、SVI・VRRP/HSRP・Port-channel・VRF が標準的に書ける |
| L2スイッチ（アクセス、管理、フロア） | Cisco Catalyst 9200/9300 系 / IOS-XE | 同上。管理用 VRF（Mgmt-vrf）の概念がある |
| ルーター | Cisco ISR / Catalyst 8000 系 / IOS-XE | 静的経路・NAT・サブインターフェースを標準記法で書ける |
| ファイアウォール | Cisco Secure Firewall ASA ソフトウェア（ASA 記法） | 専用FWの記法として最も普及しているもの。2ポートを同一セグメントに置く構成は BVI（bridge-group）で表現できる |

**同じセグメント（横線）に2ポート以上がつながる FW・ルーターの既定実装**

| 役割 | 既定 | 代替（プロジェクト既定値で指定されたら使う） | 理由 |
|---|---|---|---|
| ルーター（ISR / Catalyst 8000） | **L2 スイッチポート（内蔵スイッチポートまたはスイッチモジュール）＋ SVI（`interface VlanN`）** | BDI（`interface BDI N`）＋ EVC（`service instance` / `bridge-domain`） | L3 スイッチと同じ SVI 記法になり、図の「ルーティング箱＋横線」とそのまま対応する。ISR のスイッチポート構成が最も普及している。BDI/EVC は Catalyst 8000 などスイッチポートを持たない機種で使う |
| FW（ASA） | **BVI（bridge-group）** | 2ポートを別セグメントに分ける（図の修正が前提） | ASA で同一サブネットに複数 IF を置く標準の方法 |

どちらの実装でも**2本のリンクが同時に L2 でつながる**ため、対向がコアのペア（コア間 trunk で同じ VLAN を通す）なら L2 ループになる。採用した機種が STP に参加できるか（ASA の BVI は BPDU を転送するだけで STP に参加しない、ISR のスイッチポートは STP に参加する、など）を指摘一覧に V-06 で記録する。図の接続はそのまま設定し、ループの解消をコンフィグ側で勝手に行わない（1.3 原則）。

**ポート名の扱い**: フォールバック後も**図のポート名をそのまま使い、正式名に展開するだけ**にする（`Te0/1` → `TenGigabitEthernet0/1`、`Gi0/2` → `GigabitEthernet0/2`、`Po1` → `Port-channel1`）。実機の番号体系（`1/0/1` 等）に合わせて振り直すことはしない。図とコンフィグの対応が崩れるため。実機に合わせる対応表が必要なら別表で出す。

`Mgmt` のような汎用名は、採用OSの管理ポート名に置き換え（IOS-XE なら `GigabitEthernet0/0`）、図の名前をコメントで残す。

### 4.3 フォールバック時に必ず書く「機種判定」欄

変換レポートの冒頭に次の形式で書く。

```markdown
## 機種判定
| 機器 | 図の記載 | 判定 | 採用した記法 | 理由 |
|---|---|---|---|---|
| xx1-core01 | A社 L3SW 5000-48 | 特定不能（架空の社名・型番） | Cisco IOS-XE（Catalyst 9000 相当） | ポート名が Te/Gi/Po の Cisco 形式。L3SW として SVI・VRRP・LAG が必要で、最も一般的な記法で表現できるため。機種確定後に記法変換が必要 |
```

理由には次の3点を含める。①なぜ特定できなかったか（図の記載の何が不足か）、②なぜ Cisco のその系列を選んだか（必要な機能をその記法で表現できること、ポート名の類似、普及度）、③実機が確定したら何を直す必要があるか（ポート番号体系、冗長化プロトコル名、管理IF名など）。

### 4.4 機能の実装可否の確認

図から必要と分かる機能（LAG、VRRP、VRF、PoE、ブリッジ、NAT、10GBASE-T モジュールなど）を一覧にし、採用した機種・記法で実装できない機能があれば、指摘一覧に「機能要件」カテゴリで記録する。

## 5. 図からコンフィグへの変換規則

### 5.1 機器の役割の判定

| 図の特徴 | 役割 | 生成するもの |
|---|---|---|
| ルーティング箱あり＋多数の横線＋LAG | L3スイッチ（コア） | VLAN、SVI、冗長化、トランク、LAG、静的経路、STP |
| ルーティング箱なし＋横線あり | L2スイッチ | VLAN、トランク/アクセス、LAG、管理IF |
| ルーティング箱＋外部セグメント（INET 等） | ファイアウォール / ルーター | 外部IF、内部IF、静的経路、NAT（図かルールにあれば） |
| `vrf mgmt` ＋ `Mgmt` ポート | OOB 管理を持つ機器 | 管理用 VRF、管理IF、VRF 内の経路 |
| 管理セグメント横線上のバッジのみ | インバンド管理 | 管理 VLAN の SVI、`ip default-gateway` |

### 5.2 要素ごとの対応規則

| # | 図の要素 | コンフィグ（Cisco IOS-XE 記法の例） | 注意 |
|---|---|---|---|
| R1 | Host 欄 | `hostname <名前>` | 重複・誤記は指摘し、仮称を付けたら明記 |
| R2 | 横線＋ラベル `VLANn` / 名前 | `vlan n` / ` name <名前>` | 範囲は `vlan a-b`。名前は個別に決まらなければ省略 |
| R3 | ポートが横線1本だけに接続 | `switchport mode access` / `switchport access vlan n` | |
| R4 | ポート/Po が複数の横線に接続 | `switchport mode trunk` / `switchport trunk allowed vlan <接続した横線のVLANの和>` | **allowed VLAN は「線が来ている横線」だけ**。図に無い VLAN を足さない |
| R5 | 複数ポートにまたがる Po 箱 | `interface Port-channelN` ＋ 各物理ポートに `channel-group N mode <モード>` | モードは図に無い。ルールが無ければ `active`（LACP）を既定とし【推測】。プロジェクト既定値（1.1）や既存ルールで `on` と決まっていればそれに従う |
| R6 | Po 箱と横線の接続 | Port-channel IF とメンバーポートの両方に同じ VLAN 設定 | メンバーと Po の設定を一致させる |
| R7 | ルーティング箱と横線の接続＋バッジ `.a` | `interface Vlann` / `ip address <net>.a <mask>` | バッジが `.x` なら `<TBD>` |
| R8 | 冗長ペア線＋`vip .v` | `vrrp <g> address-family ipv4` / `address <net>.v` など（IOS 旧形式なら `vrrp <g> ip <net>.v`） | グループ番号・優先度は 6.2 |
| R9 | ルーティング箱と外部セグメントの直結ポート | ルーター/FW の L3 物理IF に IP | |
| R10 | FW/RT の2ポートが同じ横線に接続 | ルーターは L2 スイッチポート＋SVI、ASA は BVI（4.2 の既定実装） | 実装方式は図から決まらないので【推測】。L2 ループの指摘（V-06）とセット。ループが懸念でも接続は削除しない |
| R11 | `vrf X` 箱＋接続ポート | `vrf definition X` / IF に `vrf forwarding X` | 同じサブネットを GRT と VRF の両方に持つ構成は VRF 分離が前提 |
| R12 | 管理ポート（`Mgmt`）が管理SWにつながるが、vrf 箱もバッジも無い | 管理 VRF に入れ、IP は `<TBD>`【推測】 | GRT と同じ管理サブネットを持つと重複になるため |
| R13 | `PoE` 表記・AP 接続 | `power inline auto`、AP 向けの access/trunk | SSID と VLAN の対応が無ければ指摘 |
| R14 | 「予備」「未使用」と明示されたポート | `shutdown` ＋ description【図】 | shutdown にしてよいのはこれと、接続先を特定できない未接続線のポート（6.5）だけ（8.1 TBD の出力規則） |
| R15 | 端末範囲ポート（`Gi0/3-20`） | `interface range` で access ＋ `spanning-tree portfast` | |
| R16 | サーバーNIC への接続 | 仮想スイッチ内のセグメントから VLAN を決める（2.8）。サーバー側に LAG（Po）が無ければ個別ポート | `spanning-tree portfast trunk` |
| R17 | ケーブル凡例 | `description to <対向機器> <対向ポート> [<ケーブル種別>]` | 白丸（10GBASE-T モジュールで 1G 接続）は速度の注意をコメントに残す |
| R18 | 静的経路の矢印（点線＋矢印、ラベル `to<宛先>`/`default`） | `ip route <宛先> <mask> <next-hop>` | next-hop は矢印の先の機器の、**共通セグメント上のIP（冗長ペアなら VIP）** |

### 5.3 VLAN の所属を決めるアルゴリズム（L2/L3 スイッチ共通）

```
for 各ポート p（Po のメンバーは Po 単位で扱う）:
    S = p（または p を含む Po 箱）から線が出ている横線の集合
    if |S| == 0: 管理ポート・未使用・L3 IF のどれかを判定（5.1, R9, R11）
    elif |S| == 1 かつ 横線のVLANが単一ID: access
    else: trunk, allowed = S の VLAN（範囲を含む）の和
対向ポートの allowed と一致するか確認（7章 V-04）
```

### 5.4 集約表現（VLAN 範囲・アドレス範囲）の展開

- `VLAN100-199` かつ `/18` のような集約は、**VLAN定義と trunk の allowed は範囲のまま**書き、SVI と冗長化は「1 VLAN 分のテンプレート」として書く（`interface Vlan<1NN>` のように）。
- サブネット長・個別 VLAN ID・個別 VLAN 名は `<TBD>`。注記に払い出しルール（例「フロアごとに1VLAN, /24」）があれば、テンプレートのサブネット長に使う。
- 注記に**払い出し単位**（例「フロアごとに1VLAN」「業務アプリごとに1VLAN」）がある場合、trunk の allowed は次のように分ける。
  - **その単位の機器だけにつながるリンク**（例: フロアSW向けの trunk、フロアSW の端末ポート）: 範囲全体ではなく `<TBD:そのフロアのVLAN>` のプレースホルダにする。範囲全体を流すと、注記の設計意図（単位ごとの分離）と合わず、不要な VLAN が末端まで広がるため。
  - **複数の単位を通すリンク**（例: コア間 LAG、コアどうしをつなぐ経路上のリンク）: 範囲のまま書く。
  - 払い出し単位の注記が無ければ、図の線のとおり範囲のまま書き、指摘一覧に INFO で「単位ごとの絞り込みを確認」と記録する。
  - 例: 「フロアごとに1VLAN（VLAN500-599）」の注記があり、フロアSW が管理 VLAN 20 にも属する図では、コア間 LAG は `20,500-599`（他のVLANと合わせて）、コア→フロアSW の trunk は `20,<TBD:そのフロアのVLAN>`。

### 5.5 静的経路

- **静的経路は、合成図または同じファイルの他ページに経路の表現（矢印、`to<宛先>`/`default` のラベル、経路表）があるものだけを生成する。** 「不足していると思われる経路」（拠点間の戻り経路、FW から内部の集約経路など）はコンフィグに入れず、指摘一覧に L-05 の提案として書く（宛先、next-hop の候補、なぜ必要と考えたか）。経路の追加は通信の可否と制御に直結するため、図の範囲に留める。
- 合成図に経路が描かれていない場合は、同じファイルの論理構成図ページの経路矢印を使う（【論】）。
- 宛先「to東京」のような拠点名は、その拠点の全セグメントを包含する集約アドレス（拠点ブロック）に置き換える。拠点ブロックは、その拠点の全セグメントラベルの共通上位から求め、【推測】とする。
- 冗長ペア宛の next-hop には VIP を使う（矢印がペアの「機能」を指していれば）。

### 5.6 生成順序（1台分のコンフィグ構成）

```
hostname
（vrf 定義）
（spanning-tree 全体設定）
vlan 定義
SVI（VLAN ID 順）と冗長化
物理IF / Port-channel（ポート番号順。description に対向）
管理IF
静的経路（GRT → VRF）
共通管理設定（NTP/DNS/Syslog/SNMP/SSH）は値があるものだけ、無ければテンプレート
end
```

## 6. 図に無い情報の補い方（推論ルールと優先順位）

### 6.1 情報源の優先順位

| 順位 | 情報源 | 根拠ラベル |
|---|---|---|
| 1 | 利用者が与えた明示的な指定（機種、IP管理表、命名規約、設計ルール） | 【指定】 |
| 2 | 対象の合成図ページのラベル・線・バッジ・凡例 | 【図】 |
| 3 | 図中の注記テキスト（設計ルールの説明） | 【図注記】 |
| 4 | 同じファイルの他ページ（論理構成図、物理構成図、全体概要図） | 【論】【物】【概】 |
| 5 | 図内の規則性（命名・ポート番号・アドレスの規則、冗長ペアの対称性） | 【推測：規則性】 |
| 6 | 一般的な設計慣行・ベンダーの既定値 | 【一般】 |

- 2 と 4 が食い違う場合: **コンフィグには技術的に成立する方を暫定採用**し（例: 重複アドレスを避ける方）、**必ず指摘一覧に ERROR/WARN で記録**する。どちらを採ったかと理由を書く。
- 5 と 6 で作った値は、レポートの「推測一覧」にも載せる。

### 6.2 図に描かれないことが多い項目と既定の扱い

| 項目 | 既定の扱い | ラベル |
|---|---|---|
| 冗長化グループ番号 | VLAN ID と同じ番号。ただし VRRP の範囲（1-255）を超える VLAN は `<TBD>` にして指摘 | 【推測】 |
| 冗長化の優先度・プリエンプト | 01号機を優先（110）、プリエンプト有効（プロジェクト既定値があればそれ） | 【推測】 |
| LAG モード | LACP active（プロジェクト既定値・既存ルールがあればそれに従う） | 【推測】 |
| STP | 冗長経路（ラダー、三角）があれば Rapid PVST+。ルートブリッジは 01号機のコア、セカンダリは 02号機。端末・サーバーポートは portfast | 【一般】【推測】 |
| 管理IP（`.x`） | `<TBD>` | — |
| 管理VRFのデフォルト経路 | 管理セグメントの VIP（または GW） | 【推測】 |
| NTP/DNS/Syslog/SNMP | 図や他ページにサーバーのIPがあれば使い、無ければ `<TBD>` | 【論】/— |
| DHCP リレー | 端末セグメントの SVI に `ip helper-address <TBD>`（DHCP サーバーの記載があれば） | 【推測】 |
| NAT・FWポリシー | インターネットに接続する FW には NAT の雛形のみ。ポリシーは `<TBD>` | 【一般】 |
| MTU・速度・デュプレックス | 既定（設定しない）。凡例が速度変換（10G ポートで 1G 接続）を示す箇所はコメント | 【一般】 |
| 未使用ポート（図に描かれていないポート） | 設定しない（プロジェクト既定値で shutdown と決まっていれば shutdown） | — |
| 図で使用中と描かれたポート・SVI | **shutdown しない**。値が未確定なら `<TBD:...>` を有効行に置く（8.1 TBD の出力規則） | 【図】 |

### 6.3 推測してよいもの・いけないもの

| 推測してよい（ラベル付きで） | 推測しない（`<TBD>`） |
|---|---|
| 冗長ペアの片側の省略部分（対称性） | 個々のIPアドレスのホスト部が `.x` のもの |
| 規則性のあるポート番号（サーバー番号とポート番号の対応など） | ISP・通信事業者側のアドレスや GW |
| 誤記と判断できるもの（例: 10G ケーブルなのに `Gi` 表記） | 個々の VLAN ID・サブネット（集約表現の中身） |
| VLAN 名、description | セキュリティポリシー、認証情報、SNMP コミュニティ |

### 6.4 誤記と判断するときの基準

次のいずれかを満たすとき「誤記の可能性が高い」とし、コンフィグでは修正値を採用してもよい（指摘は必須）。
- 同じ図の対称な要素と1か所だけ違い、その違いに技術的な意味が無い（例: 02号機だけポート名の系列が違う）
- 凡例（線種）と矛盾する（例: 10G 光ケーブルの端点が 1G ポート名）
- 他の情報源（別ページ、注記の規則）と食い違い、しかも図の値のままでは設定が成立しない（例: アドレス重複）

### 6.5 未接続線（片端が図形につながっていない線）の扱い

drawio の source/target が空の線（ツール EDGE_DANGLING、7章 P-01）は、次の3条件で扱いを決める。

| 条件 | 確認すること |
|---|---|
| ① もう一端 | つながっている側のポート（機器・ポート名）が分かる |
| ② 線の向き・座標 | 未接続の端点の座標が、どの機器・ポートの近くで終わっているか。線の向き（どの機器に向かっているか） |
| ③ 裏付け | 対称性（冗長ペアの相手機器では同じ位置のポートがつながっている）、規則性（サーバー番号とポート番号の対応など）、他ページ（物理構成図の結線） |

- **①②③がすべてそろう場合**: 推定した接続先との接続として**設定する**（description に推定と書く）。指摘一覧に WARN（P-01）で記録し、「推定した接続先」と「裏付け」を書く。図の設計意図に沿うのはこちらで、接続先を直せば済む描画ミスである可能性が高いため。
- **③の裏付けが無い場合**: ポートは description に「接続先不明」と書いて **shutdown** にし、指摘一覧に WARN（P-01）で記録する。存在が確かでない接続を有効にしないため。
- 推定したかどうか、どちらを採ったかは、変換レポートの根拠表と推測一覧（8.1）にも書く。
- サーバー・VM の中の未接続線（仮想スイッチと VM の間など）も同じ基準で推定し、スイッチ側の VLAN 所属の根拠に使うかどうかを決める。

## 7. 整合性チェック（レビュー観点のチェックリスト）

全項目を実施し、該当があれば指摘一覧（8.2）に1行ずつ記録する。「該当なし」の結果もレポートに残す（チェック済みであることを人が確認できるように）。

**重要度**
- **ERROR**: そのままでは設定できない、または確実に動作しない（アドレス重複、存在しない接続先、VLAN の不一致）
- **WARN**: 矛盾や誤記の疑い、設計上のリスク（名前重複、図面間の不一致、L2ループ、機能不足の可能性）
- **INFO**: 図に無い情報（推測・TBD で補った）、省略表現の解釈

### 7.1 命名・識別（N）

| ID | チェック | 方法 | 既定の重要度 |
|---|---|---|---|
| N-01 | ホスト名の重複 | 機器台帳で同名を検出（ツール HOSTNAME_DUP） | WARN |
| N-02 | ホスト名の命名規則違反 | 拠点接頭辞・役割・連番の規則から外れるもの（例: 大阪の箱に東京の接頭辞） | WARN |
| N-03 | ページ間での名前の違い | カラー版/モノクロ版、合成図/論理構成図で同じ機器の名前が違う | WARN |
| N-04 | ラック・フロア名の重複・誤記 | 配置単位の枠のラベル | INFO |
| N-05 | ポート名の重複（同一機器内） | 1台に同じポート名が2つ | ERROR |

### 7.2 アドレス（A）

| ID | チェック | 方法 | 既定の重要度 |
|---|---|---|---|
| A-01 | セグメント間のアドレス重複・包含 | セグメント台帳の CIDR を拠点内・拠点間ですべて比較（ツール CIDR_CONFLICT は完全一致のみ検出。包含は手で確認） | ERROR |
| A-02 | 拠点ブロック外のアドレス | 拠点のブロック（例 拠点A 10.1.0.0/16）から外れるセグメント | WARN |
| A-03 | バッジのIPがサブネット外・ネットワーク/ブロードキャストアドレス | `/27` で `.40` など | ERROR |
| A-04 | 同一セグメントで同じIPを持つ機器が複数 | バッジの重複（VIP を含む） | ERROR |
| A-05 | 冗長ペアのIP規則の不一致 | 01/02/vip の規則がセグメントによって違う、または別ページの規則と違う | WARN |
| A-06 | バッジの表記揺れ | ドット欠け（`2`）、未確定表記（`.x`）の残存 | INFO（`.x` は TBD 一覧へ） |
| A-07 | 拠点間で同じアドレスのラベルの使い回し | コピー&ペーストの残り（大阪の図に東京のアドレス） | ERROR/WARN |

### 7.3 VLAN・L2（V）

| ID | チェック | 方法 | 既定の重要度 |
|---|---|---|---|
| V-01 | VLAN ID の重複（異なるセグメント名に同じID） | セグメント台帳 | ERROR |
| V-02 | 同じセグメント名で VLAN ID が拠点・機器によって違う | 同上 | WARN |
| V-03 | ラベルが無い横線、横線につながらないラベル | ツールの「横線→ラベル」と要素一覧 | WARN |
| V-04 | リンク両端の VLAN 所属の不一致 | 結線表の両端のポート所属表を比較（allowed VLAN の差、access と trunk の不一致） | ERROR |
| V-05 | VLAN の通り道の断絶 | SVI を持つ機器から、そのVLANを使う末端ポートまで、trunk の連鎖で到達できるか | ERROR |
| V-06 | L2 ループ | 同じ VLAN を通すリンクで閉路ができるか（コア間 LAG ＋ 下位機器への二重接続、FW/RT の2ポートが同一 VLAN、管理SW経由の迂回など）。閉路があれば STP 前提か、機器が STP に対応するかを指摘。**ループの懸念があっても図の接続・VLAN 所属はコンフィグから外さない**（1.3 原則。該当行に `! WARN R-xxx`） | WARN |
| V-07 | VRRP グループ番号の制約 | VLAN ID をグループ番号にする規則で 255 を超えないか | WARN |
| V-08 | VLAN の孤立（コンフィグ側の自己点検） | SVI を作った VLAN、またはルーティング箱と線でつながる VLAN が、その機器の**どのポート・Po にも出ていない**ことが無いか。出ていなければ、その SVI は誰とも通信できない。図にそのような所属があるのにコンフィグから落としていれば生成ミス、図にも無ければ図の不足 | ERROR |
| V-09 | 図とコンフィグの VLAN 所属の差分（コンフィグ側の自己点検） | ポート所属表（3.3、図から作った表）と、生成したコンフィグの access VLAN / trunk allowed を**全ポートで突き合わせる**。図で横線につながっている VLAN を allowed から外していないか、図に無い VLAN を足していないか。差があれば、その理由（6.4 の誤記修正、5.4 の払い出し単位など）がレポートに書かれていること | ERROR（理由の記載が無い差） |

### 7.4 物理・ポート（P）

| ID | チェック | 方法 | 既定の重要度 |
|---|---|---|---|
| P-01 | 線の未接続（片端が図形につながっていない） | ツール EDGE_DANGLING。機器間のケーブルだけでなく、**機器・サーバー・VM の箱の中の線**（ポートと横線、VM の eth と仮想スイッチ、ルーティング箱と横線）も対象。扱いは 6.5 | WARN |
| P-02 | 1つの物理ポートに複数のケーブル | ツール PORT_MULTI_LINK | ERROR |
| P-03 | ポート名と線種（速度）の矛盾 | `Gi` に 10G 光、`Te` に 1G の場合は凡例の白丸（変換モジュール）の有無を確認（ツール SPEED_MISMATCH は前者のみ） | WARN |
| P-04 | 両端のコネクタ・ケーブル種別の不一致 | 光と銅、SR と LR など | ERROR |
| P-05 | 機種のポート数・種類との整合 | 機種名の末尾（-24, -48）とポート番号の最大値、Te/Gi の数 | WARN |
| P-06 | LAG メンバーの対向不一致 | Po のメンバーが別々の機器に向いている場合、MLAG/スタックが必要（図に無ければ指摘） | WARN |
| P-07 | LAG 番号・メンバー数の両端不一致 | 両端の Po の本数 | WARN |
| P-08 | 冗長化の片肺 | 冗長ペアなのに片方にだけある接続・ポート（対称性の崩れ）。省略か誤りかを判断 | INFO/WARN |

### 7.5 L3・冗長化（L）

| ID | チェック | 方法 | 既定の重要度 |
|---|---|---|---|
| L-01 | ルーティング箱の無いセグメントにゲートウェイが無い | 末端ノードのあるセグメントに SVI/GW があるか | WARN |
| L-02 | 冗長ペアの片方にしか SVI/バッジが無い | 両機器のバッジ | WARN |
| L-03 | 冗長化プロトコルの不一致 | 凡例と注記・別資料の食い違い（VRRP と HSRP） | INFO |
| L-04 | 静的経路の next-hop が直接接続セグメント上に無い | next-hop と自機の SVI のサブネットを比較 | ERROR |
| L-05 | 経路の欠落・非対称 | 全セグメント間（拠点間を含む）に往路と復路の経路があるか。デフォルト経路の行き先。不足する経路はコンフィグに足さず、ここに「追加案（宛先・next-hop 候補・理由）」として書く（5.5） | WARN |
| L-06 | VRF 間の到達性 | 管理 VRF から NTP/DNS/Syslog に到達する経路があるか | WARN |
| L-07 | 冗長ペアのセグメントの L2 連続性 | 冗長ペア（VRRP/HSRP）を組む各セグメントが、ペアの2台の間で L2 的につながっているか。コア間 trunk / LAG の allowed に含まれるか、または別の L2 経路（下位スイッチ経由など）で連続しているかを、**図とコンフィグの両方**で確認する。つながっていなければ冗長化プロトコルの通信が届かず、両方がマスターになる | ERROR |

### 7.6 管理・運用（M）

| ID | チェック | 方法 | 既定の重要度 |
|---|---|---|---|
| M-01 | 管理IFの無い機器 | 管理用のバッジ・Mgmt ポート・管理VLAN の SVI のどれも無い機器 | WARN |
| M-02 | 管理経路の単一障害点 | 管理通信が1本のリンクにしか依存しない機器 | WARN |
| M-03 | OOB とインバンドの混在 | 同じ管理セグメントに OOB 機器とインバンド機器が混在するときの到達経路 | INFO |
| M-04 | 管理サービスの所在 | NTP/DNS/Syslog/SNMP サーバーの IP が図か他ページにあるか | INFO |

### 7.7 図面間の整合（X）と描画品質（D）

| ID | チェック | 方法 | 既定の重要度 |
|---|---|---|---|
| X-01 | 合成図と論理構成図のセグメント・アドレス・VLAN の一致 | セグメント台帳を両ページで作って比較 | WARN |
| X-02 | 合成図と物理構成図の機器・結線の一致 | 機器台帳・結線表を比較 | WARN |
| X-03 | カラー版とモノクロ版のラベル差分 | 両ページの全テキストの差分 | INFO |
| D-01 | 凡例に無い色・線種の使用 | 凡例の対応表との比較 | INFO |
| D-02 | 線の交差でつながりが曖昧な箇所 | 目視（ジャンプ記号の有無） | INFO |
| D-03 | 所属線の色と、接続先の横線の色の不一致 | ポート・Po・ルーティング箱から横線への線の色が、その横線の色と違う（例: COMMON の横線に緑の線）。コピー&ペーストの残りや、つなぎ先の間違いの可能性がある。**接続先（drawio の source/target）を正として VLAN 所属を決め**、色の違いを指摘する（ツール LINE_COLOR_MISMATCH） | WARN |
| D-04 | 所属線がセグメントのラベルにつながっている | ポートの線が横線ではなく、横線のラベル（`... VLANn` のテキスト）に接続されている。見た目では横線に届いていても、データ上は所属が成立していない。ラベルが示すセグメントへの所属として設定し、指摘する（ツール EDGE_TO_LABEL） | WARN |

**TBD の出力規則**

ナレッジの利用者や依頼文によって出力が変わらないよう、未確定値と懸念の書き方を固定する。

1. **`<TBD:内容>` は有効な設定行のまま置く**（例: `ip address <TBD:MGMTのIP> 255.255.255.0`）。コメントアウトしない。そのまま投入すると構文エラーになるので、置換漏れに必ず気付ける。
2. **図で使用中と描かれたポート・SVI・経路は shutdown・コメントアウトしない。** 値が決まらない部分だけを `<TBD:...>` にする。
3. **shutdown にするのは次の2つだけ**: ①図で「予備」「未使用」と明示されたポート（R14）、②接続先を特定できない未接続線のポート（6.5）。プロジェクト既定値で「未使用ポートは shutdown」と指定されていれば、図に描かれていないポートも shutdown にしてよい。
4. **設計上の懸念がある行**には、行末または直前に `! WARN R-xxx <要旨>` のコメントを付けるだけにする（1.3 原則）。
5. レポートの「未確定値（TBD）一覧」に、全 TBD を設定行の単位で載せ、**投入前に置換が必要なもの**（構文エラーや誤動作になるもの）に印を付ける。投入できる版が要る場合は、この一覧を埋めてから置換する運用とする。

**冗長ペアの出力**: 既定は全台分の完全なコンフィグ。プロジェクト既定値（1.1）で「差分表」と指定された場合だけ、1台を完全なコンフィグで示し、もう1台を差分表にしてよい。

### 8.2 B. 指摘一覧（レビューシート）

人が drawio を開いて修正し、状態を記入しながら使うことを前提にした表です。Markdown（読む用）と CSV（表計算で管理する用）の両方で出力します。

| 列 | 内容 | 記入者 |
|---|---|---|
| ID | `R-001` からの連番 | AI |
| 重要度 | ERROR / WARN / INFO | AI |
| チェックID | 7章のID（N-01 等） | AI |
| ページ | drawio のページ名 | AI |
| 対象 | 機器名・ポート名・セグメント名 | AI |
| 図の位置 | drawio の **cell id** と座標（x,y）。人が図形を探すため | AI |
| 図の記載 | 図に書かれている値（原文のまま） | AI |
| 問題 | 何が矛盾・不足しているか | AI |
| 根拠 | 矛盾の根拠（比較した相手の記載や、技術的な理由） | AI |
| 推奨対応 | 図をどう直すべきか（候補が複数あれば列挙） | AI |
| コンフィグでの暫定扱い | 書き起こしで採用した値と、その理由 | AI |
| 状態 | 未確認 / 図を修正済み / 対応不要 / 保留 | 人 |
| 確認者・日付 | | 人 |

**図形の探し方（推奨対応に添える）**: drawio で「編集 > 検索」（Ctrl+F）でラベルを検索するか、「その他 > 図の編集」（Extras > Edit Diagram）で XML を開き、cell id で検索する。

**CSV の書式**: UTF-8（BOM 付き。表計算ソフトで文字化けしないように）、カンマ区切り、全項目をダブルクオートで囲む。見出し行は上表の列名。

```

### 10.1 Cisco IOS-XE 記法のテンプレート（抜粋）

```
fhrp version vrrp v3
interface Vlan10
 description DMZ 10.1.10.0/24
 ip address 10.1.10.1 255.255.255.0
 vrrp 10 address-family ipv4
  address 10.1.10.3 primary
  priority 110
  preempt
```
※ 旧 IOS 記法（`vrrp 10 ip 10.1.10.3`）や HSRP（`standby 10 ip 10.1.10.3`）を使う場合は、レポートでどれを採ったかを明記する。

トランク（LAG）:
```
interface Port-channel1
 description to <peer> Po1
 switchport mode trunk
 switchport trunk allowed vlan 20,30,500-599
!
interface range TenGigabitEthernet0/23 - 24
 description to <peer> Te0/23-24 (Po1)
 switchport mode trunk
 switchport trunk allowed vlan 20,30,500-599
 channel-group 1 mode active
```
※ 古い Catalyst では `switchport trunk encapsulation dot1q` が必要。`switchport nonegotiate` などの付加コマンドは、プロジェクト既定値（1.1）で指定されたときだけ付ける。

 address-family ipv4
!

```
